# Правило версий PDF Compressor: релизная линия + постоянная тестовая линия

**Согласовано с пользователем 14 ноября 2026.** Тестовый функционал должен быть **встроен в отдельную полноценную сборку PDF Compressor**, а не предоставляться в виде внешнего скрипта. Тестовую сборку использовать для внутреннего тестирования всех будущих релизов. Не публиковать её как пользовательский релиз и не переносить журнал тестов в стабильную сборку без отдельного прямого решения.

## Две линии разработки

1. **Релизная линия**: `main` + временная ветка разработки соответствующей версии (например, `develop/2.8-quality-audit`, потом отдельная `develop/2.9-…`). Только после проверки пользователь подтверждает слияние в `main` и выпуск обычного `v2.8`, `v2.9` и т.д.
2. **Непрерывная тестовая линия**: полнофункциональная программа с добавленным автоматическим журналом тестов и экспортом ZIP. Ветки называются `testing/2.8.1-automatic-test-report`, затем `testing/2.9.1-automatic-test-report`, далее `testing/3.0.1-automatic-test-report` и т.д. Суффикс `.1` — **наша внутренняя версия для тестов**, а не обязательный публичный патч-релиз. Она должна оставаться отдельной от `main`.

## Схема ближайших обновлений

```text
                        ┌─ develop/2.8 ── release v2.8 ── main
2.7.1 stable ── main ───┤                          │
                        └─ testing/2.8.1 <─────────┘
                           [полная программа +
                            внутренний отчёт]

main(v2.8) ── develop/2.9 ── release v2.9 ── main
                  │                         │
                  └─ интеграция изменений ─┘
                         ↓
testing/2.8.1 ── testing/2.9.1
                  [тот же встроенный отчёт +
                   все новые функции 2.9]
```

**Для 2.8**: завершаем разработку обычной 2.8; после её релиза подтягиваем **ровно соответствующий стабильный код 2.8** в уже существующую отдельную тестовую ветку 2.8.1. Изменения идут **из релизной ветки в тестовую**, но **никогда в обратную сторону**. В тестовой сборке останутся все функции 2.8 и встроенный экспорт тестов.

**Для 2.9**: разрабатываем 2.9 в собственной, новой релизной ветке независимо от тестовой. Для тестов переносим изменения 2.9 в новую ветку **`testing/2.9.1-automatic-test-report`**, которую продолжаем от 2.8.1, сохраняя её отчёты, историю и исправления. В GUI и имени тестового EXE обновляем маркировку с `2.8.1-testing` на `2.9.1-testing`. Старую ветку 2.8.1 можно сохранить в истории как зафиксированный этап — это не выпуск 2.8.1 в релизах.

Повторяем ту же схему для каждой следующей релизной версии. Если есть конфликт после объединения, разрешаем его с приоритетом **сохранности и правильной работы движка релизной версии**, отдельно проверяем тестовые функции; ничего не затираем автоматически.

## Жёсткие ограничения

- **Запрещено сливать тестовую ветку в `main` или в обычную релизную ветку**: иначе механизм внутреннего журнала попадёт в релиз. Ветка тестов может получать изменения обычных версий, но не наоборот.
- Не создавать публичные `v2.8.1`, `v2.9.1` и т.п. из внутренней тестовой линии. Тестовый EXE — только GitHub Actions artifact **NOT FOR RELEASE** или прямо согласованная приватная передача.
- Внутренняя тестовая программа — **полная программа PDF Compressor** со всеми кнопками обычной версии, плюс два действия: `Экспорт отчёта тестов (ZIP)` и `Очистить историю тестов`.
- Журнал автоматически пишет размеры до/после, времена, режимы, параметры, достижение лимита, количество страниц, результат проверки качества, отмены и ошибки; не требует ручных скриншотов. Только локальная запись, без телеметрии в сети.
- При обновлении до следующего `.1` сохранить **формат и обратную совместимость отчёта** или документировать миграцию схемы. История тестов должна пережить обновление приложения; если меняется путь к данным, добавить корректную миграцию.
- После синхронизации с любой новой базовой версией провести Windows CI, тесты GUI/журнала, тесты на отмену/пакет и сборку одного EXE, **прежде чем давать обновлённую тестовую версию пользователю**.
- Не объединять и не публиковать обычную версию автоматически. Нужна приёмка пользователем.
